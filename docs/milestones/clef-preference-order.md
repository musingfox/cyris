# Clef 進選文：只決定 digest 的排序

2026-10-10 經一層設計討論定案，屬於 m-embedding-preference（Obsidian vault `pm/cyris/tasks/m-embedding-preference.md`）。開發輪量測的腳本與原始資料不入 repo，數字與做法記在 vault `pm/cyris/tasks/jev-feature-vector-eval.md` 的 2026-10-09 段。

## 這個里程碑定下什麼

Clef 第一次碰生產選文只做一件事：在 digest 現有的投票排序裡，用 Clef 判斷的「讀者會按讚的機率」取代 embedding 的 cosine 差值，當作排序依據。它不改變任何文章的保留或淘汰，不蓋 `triaged_at`，filter 的判斷原封不動；它放在一個 grade D 開關後面，預設維持現在的 cosine 排序，只有在 2026-10-14 前後的驗收輪證明它有用之後才打開。送給 Clef 的請求要帶判斷依據：相近投票的標題（讚與倒讚分開），加上明文寫出的選文條件。驗收輪的主要數字只用「文章進來之前已經有的投票」當相近投票。

## 已經具體到可以往下做的部分

- **判斷的範圍**：只判斷已經進到這一期的項目，也就是 filter 保留的標題加上 Features。每輪是幾十次呼叫，不是整個候選池的約 200 次。整個候選池的影子分數不在這一層做，它只對未來的淘汰門檻有用，而淘汰屬於 M-behaviour。
- **排序接在哪裡**：沿用現有的投票排序。現在 `_vote_preference` 把 vote similarity 的 `net`（最像的讚減最像的倒讚）交給排序（`src/cyris/service_layer/run_digest.py:58-69`）。Clef 版本提供同樣形狀的「每篇一個分數」，排序與 15 項上限的截斷邏輯不變。
- **不動文章狀態**：被上限截掉的文章維持 pending，下一輪重新過 filter（`src/cyris/service_layer/digest_pipeline.py:222-231`）。所以只改排序不會動到盲標用來分層的「保留／被刪」。
- **每篇的請求內容**：
  - 文章本身：標題、來源、內文前 1000 字，和生產評分相同。
  - 相近投票：最近 5 篇讚、最近 5 篇倒讚的標題，只放標題，不放內文。開發集上加內文會從 0.754 掉到 0.682。
  - 判斷條件：明文的選文條件，這是使用者的要求。
  - 每次請求只問一題 `noul`，因為同一請求裡的題目會互相影響。
- **失敗時的行為**：Clef 呼叫失敗或沒有相近投票時，這一期退回現在的排序，並記下原因。現有的 `unranked_reason` 就是這個用途。run 不會因為 Clef 失敗而失敗。
- **收據**：run summary 要記錄這一期用了哪一種排序依據、哪個模型，以及日期。Clef 不能鎖版本，模型可能在沒有通知的情況下更新。
- **成本**：
  - 上限：每輪 200 篇、每天 2 輪，每次約 472 token，約每天 1.5k neurons，Workers AI 每天免費 1 萬 neurons（定價見 https://developers.cloudflare.com/workers-ai/platform/pricing/ ，每百萬 flash token 約 8,182 neurons；token 數取開發輪 59 題請求的中位數）。
  - 只判斷進到這一期的項目，實際用量更低。
- **驗收輪**：
  - 抽樣：約 2026-10-14 跑 `uv run cyris labels draw --since 2026-10-08T16:12Z --seed 2 --replace`，標完後在開關打開之前離線計分。
  - 主要數字的種子規則：種子投票的 `triaged_at` 要早於候選文章的 `first_seen_at`（`src/cyris/adapters/store/schema.sql:37,42`）。`triaged_at` 是同步時間，但同步之後的那一輪確實拿得到這票，所以這個切點是正確的。
  - 主要比較：上線版本的請求形狀（相近投票加判斷條件）對上 embedding 偏好，在 filter 保留的那一層算 AUC，附配對 bootstrap 信賴區間。
  - 為什麼看保留層：排序只作用在保留層。原本 vault 卡片指定的主要比較是全部題目；改成保留層，是因為這次只上線排序。開發集保留層上，Clef 加 5 篇是 0.787，embedding 是 0.580。
  - 次要數字：
    - 用所有投票的規則算一次，可以和開發輪的 0.754 對照。
    - 只放投票標題、不放判斷條件的版本也算一次。
    - 全部 100 題也算一次。
  - 打開開關的條件：主要比較的配對差，95% 信賴區間下界大於 0。這個門檻在抽樣前就定下，看過數字之後不改。

## 刻意留給實作時決定的事

- **判斷條件的文字從哪裡來，屬於第幾級設定。** 開發輪量過的是直接拿 `FILTER_SYSTEM` 的條件當備援（`src/cyris/service_layer/prompts.py:43-80`），但這些條件在非新聞上和讀者標記幾乎無關（LLM 保留判斷 0.517）。可能的做法有三種：照搬、只取內容類型那幾條，或改成讀者在 `/settings` 可編輯的文字（grade D）。現在選太早，因為要先看驗收輪裡「加條件」和「不加條件」的差距。
- **決策模型走 Protocol 還是直接注入。** Jev 的 API 形狀相同，所以確實存在第二種實作。這是內部的事，可以反悔。
- **clef 還是 clef-flash、k 取多少、相近投票怎麼取。** 現在的 `judge()` 只回傳最像的一讚一倒讚（`src/cyris/domain/similarity.py:88-96`），要擴成前 k 篇。這屬於實作層。
- **和 vote similarity 校準門檻的耦合。** 現在只有在 vote similarity 有校準過的門檻時才有排序（`run_digest.py:64-69`）。Clef 排序要沿用這個條件還是拆開，要等實作層看過接線再決定。
- **開關的形狀。** 可以在既有的 `digest.rank_by_preference` 旁邊加一個「排序依據」的值，也可以另開一個開關。兩者都是 grade D，都可以反悔。

## 什麼會推翻這個決定

- **驗收輪顯示 Clef 在保留層沒有勝過 embedding**：只用事前投票時，配對差的信賴區間包含 0。這種情況下開關保持關閉，Clef 整合退回「先不做」，排序繼續用 cosine 或乾脆關掉。
- **正式站的上限很少截到標題**：要讀 D1 `digest_runs.summary` 裡 2026-10-08T12:30Z 之後的 `preference_rank_moved_headlines`。如果幾乎為 0，排序的槓桿很小，這份工作買不到什麼。尚未查證，要由使用者讀正式站 D1。
- **驗收輪裡「加判斷條件」重現開發輪的非新聞下降**：開發輪是 0.670 降到 0.619。這種情況下條件只留給新聞，或者拿掉條件。
- **新聞層因為分群投票的扇出而偏高**：對分群新聞的投票會寫到群內每一篇的網址上，近乎重複的標題就會進到種子裡。這個風險尚未查證，要讀正式站 D1 才能確認。若屬實，新聞層的主要數字要排除同群種子再算。

落選的方向：
- 先不做：五個未解問題沒有一個會因為等待而有答案。
- 只記影子分數：資料只對淘汰門檻有用，而淘汰不在本 milestone 範圍。
- 排序加影子分數：理由同上，範圍變大卻沒有用途。
- 救回被刪的文章：filter 最常誤刪的非新聞被刪層，Clef 只有 0.583。救回的文章收到的票會永久留在種子裡。
- 接手保留與淘汰：之後每一票都只落在 Clef 放行的文章上，偏差無法從資料裡拿掉，而且違反本 milestone「不用投票刪文章」的範圍。
