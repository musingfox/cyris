# 重構資訊流：單位是主題，骨架是領域

**2026-10-29 被 [digest-pebble-sand-water.md](digest-pebble-sand-water.md) 與 [ADR-0023](../decisions/0023-votes-go-on-topics-and-the-digest-has-three-layers.md) 取代。** 新的設計以 pebble、sand、water 三層取代領域骨架（L1、L3），以 sand 與 water 取代合成段落（L4），取消卡片掛接與論點對照（L2），拿掉輸出截尾，票改投在跨期的題目上。已上線的 L1 與 L4 程式留到新里程碑的 `retire-area-skeleton` 再拆。lane 改名（Lr）、filter 分批（Lb）與模型評比（Lm）不在新設計的推翻表裡。以下內容是當時的決定，保留作為歷史。

2026-10-11 經五層設計討論定案，起點是「tier 分層還有沒有必要」。結論是有，但 tier 的角色改了：它決定一篇文章預設以什麼形式出現，逐篇的值決定它排哪裡、上不上。這份文件只管版面和分類；逐篇的值、點開紀錄、拿掉 `rejected` 的工作留在 `value-by-clicks-and-rank.md`，這裡的階段依賴那邊的收據。

## 這個里程碑定下什麼

- **tier 決定形式，不決定層級。** 新聞（`filter`，量多、密度低）預設分群後寫成段落，確認同主題的才掛到卡片底下；專欄與電子報（`summarize`，密度高）預設拿卡片；粉絲向（`fan`）直通、不截斷。這三層就是現有的 `Tier`（`src/cyris/domain/models.py:15-20`、`docs/architecture.md:310-316`）。一篇值夠高的新聞可以離開新聞的形式，拿到自己的卡片。
- **三層改名為 `skim`、`read`、`follow`。** 2026-10-11 讀者定案。`filter` 和 `summarize` 說的是 pipeline 對來源做什麼，tier 改成只決定形式之後就名不符實；新名字說的是讀者對這類來源做什麼，形式再變、讀者的動作不變。`fan` 的程式註解本來就寫 followed groups/newsletters。欄位名 `tier` 帶著上下階級的意思，也不對，同日定案一起改成 `lane`：`sources.yaml` 的 `lane:`、`SourceConfig.lane`、D1 的 `stored_articles.source_lane`。lane 是三條平行的路，沒有上下。改 D1 欄位名是這個專案第一次演化既有部署的 schema（見 Lr），要寫 ADR。
- **卡片預設是單篇摘要，有同主題的新聞才寫論點對照。** 2026-10-11 第三次定案，依 MVP 的數字（見「依據的資料」）：密度高文章多是不跟當日新聞走的分析和隨筆，同一天裡「同一事件、公司、政策」的新聞兩天六個錨點只出現一次。所以卡片就是今天的 Features，一篇一張；當嵌入找出的候選經 LLM 確認真的同主題，卡片底下才掛那幾篇，摘要改寫成錨點與新聞之間不同的論點、逐論點標出處。對照是例外形，大約每週一張。2026-10-02 的「一張卡片一篇文章」因此大致維持，ADR 只記這個例外：確認過的同主題新聞可以掛在卡片底下、進入它的摘要，追溯性由逐論點的出處保住。
- **「單位是主題」的重心在剩餘新聞。** 多篇同題真正發生的地方是新聞彼此之間：嵌入分群在 0.70 做出國慶酒會 9 篇、徐佳青請辭 6 篇這種真的故事群。剩餘新聞的形式是先分群、再把全部單位分批寫成段落，重要的在前，由領域配額截尾（N1 已選 c）。
- **版面骨架照類型，骨架裡面照品質。** 每個領域一個區段，區段內上層是主題卡片（值得讀），下層是緊湊的「需要知道」列，兩層內部各照值排。今天的七個區段依 pipeline 的機制排（`docs/design/ui-language.md:292-296`），對讀者沒有意義，整段重寫。
- **領域由 LLM 從讀者的來源分出來，讀者確認。** 來源加入時分類一次；每篇文章在既有領域的封閉集合裡選一個，另外可以提議新領域。提議只是提案，要在幾期內被夠多篇文章重複提出、再由讀者在 `/settings` 命名確認，才成為區段。名稱由讀者擁有。
- **領域有老化，衰減回基線。** 讀者排的領域順序是基線；近期的點開率把某個領域的權重暫時推高，沒有新行為就按半衰期退回基線。權重改那個領域的配額和上下層分界，不改區段順序。
- **沒有密度高文章的期，只是版面問題。** 不把密度高的文章扣著等下一期，也不只為 `summarize` 拉長窗口。

## 已經具體到可以往下做的部分

上面「定下什麼」裡，tier 決定形式、新聞可以升格、單位是主題、領域由 LLM 分加提案、領域要老化，這五項是讀者自己說的；「骨架照類型」和「衰減回基線、改配額不改順序」是討論中提出的形狀，讀者沒有反對就往下走。這一節的機制全部屬於後者：是目前的形狀，不是定案，之後的讀者可以挑戰。

- **掛接是嵌入初選加 LLM 確認，分群只用嵌入。** topic tracking 把一句描述嵌入後和每個候選標題比餘弦，門檻隨嵌入模型存（`src/cyris/service_layer/tracking.py:40-93`）。vote similarity 這一輪已經嵌入過每個候選標題，tracking 重用那些向量（`tracking.py:4,58`、`src/cyris/service_layer/vote_similarity.py:98-99`），所以嵌入的部分幾乎不增加呼叫。但餘弦本身切不開掛接：MVP 顯示標題餘弦擠在 0.50 到 0.65 之間，0.55 到 0.60 有斷崖，0.60 掛上的一半不同主題。所以掛接分兩步，嵌入替每個錨點取餘弦前 8 名（下限 0.50），再由一次 LLM 呼叫確認哪些是同一事件、公司、政策或問題；每個錨點多一次呼叫，每天三到六次。候選數和下限是 grade D 設定，下限隨模型存（ADR-0006 的規則）。剩餘新聞的分群不經 LLM，餘弦 0.70 起試。兩篇密度高文章碰巧寫同一主題時維持兩張卡片，和今天一樣；L0 顯示這種情況每期幾乎不會發生，不值得一個合併步驟。
- **今天的合併看標籤，不看內容。** summarize 依來源的第一個標籤分組，一組一次摘要（`src/cyris/service_layer/summarize.py:17-23,38`）；Top story 只在同一組有兩篇以上過 `featured_threshold` 時聚合（`src/cyris/domain/selection.py:63-88`）。兩份電子報寫同一件事、標籤不同，現在是兩張卡片。
- **新聞的 LLM 分群刪掉。** `cluster_news`（`src/cyris/service_layer/cluster_news.py`，由 `src/cyris/service_layer/digest_pipeline.py:154` 呼叫）被嵌入掛接取代。未驗證：session 記憶說正式站 67 個新聞群組全是單篇，可從 D1 `stories`、`story_members`（`src/cyris/adapters/store/schema.sql:126-146`）重查。
- **領域的資料住三個地方，只加一張表。** 領域清單是新表 `areas`：名稱、順序、狀態（提案或啟用）、提案次數，grade D，`/settings` 寫，和 `tracked_topics` 同一個模式（`schema.sql:77-81` 的註解說明為什麼不放 `settings`）；`docs/architecture.md` §4 加一列。來源到領域放 `sources.config` JSON（`schema.sql:70-75`），不加欄位，因為 `ADD COLUMN` 到不了既有部署。文章到領域不另存：位置是那一期的屬性，跟著進 `digests` 的 JSON（`schema.sql:186-193`）。
- **逐篇分類不加 LLM 呼叫。** 評分 prompt 已經要 LLM 給每篇文章 topic tags（`src/cyris/service_layer/prompts.py:245-267` 的 `SCORING_SYSTEM`），寫進 `tags` 詞彙表和 `article_tags`（`src/cyris/adapters/store/tags.py:16`、`schema.sql:154-158`）。在同一個輸出 schema 裡多一個「從這些領域選一個」和一個「都不是，建議 X」欄位就夠。評分跳過帶 `news` 標籤的來源與 `fan`（`src/cyris/service_layer/scoring.py:27-33`），這些文章沒有逐篇改選的機會，位置只看來源層；`sources.yaml` 的新聞來源本來就按版面分成獨立來源（中央社的政治、財經、國際、科技各是一個），來源層的領域足夠。filter prompt 不改。現有的自由標籤留著合併主題用，不拿來決定位置。
- **跨領域的歸屬。** 一個主題的領域跟著它錨點那篇密度高文章；只有新聞的主題跟著多數成員。來源層給預設，文章層可以在封閉集合內改選。
- **領域權重的輸入是每個曝光的點開率，不是點開次數。** 選舉期間政治新聞本來就暴增，用次數會富者愈富。曝光紀錄是 `value-by-clicks-and-rank.md` S3 已經決定要收的。沒點開不扣分，只靠時間衰減。半衰期和基線下限是 grade D 設定，進 §5。
- **錨點活幾天，領域權重活幾週。** 一個主題幾期沒有新文章就不再收新聞；領域權重的半衰期以週計。追蹤的主題（`tracked_topics`）今天不過期，老化在那裡只該是 `/settings` 的退休建議，不在這份里程碑的範圍。
- **email 版面一起改。** `docs/design/ui-language.md:456` 規定 email 的區段順序，骨架換掉時同一個改動裡處理。
- **每一個 LLM 請求都保持在 100K token 以內，filter 也改分批。** 這是把 pipeline 和模型脫鉤的條件：claude-haiku-5-5 的 $0.10/$0.50 只適用於 100K 以內的提示，超過是 $0.50/$2.50；gpt-6-luna 在 272K 以上整個請求輸入兩倍、輸出 1.5 倍。過去最大的請求是 filter 把一個窗口的新聞一次送進一個 prompt（`docs/architecture.md` §5 的「Provider defaults, and why these values」），實測一天 233 篇、預設 500 字元的摘錄約 22K token，一期約 11K，離門檻十倍（見「依據的資料」）。但這個請求隨來源數線性成長，而且 architecture 過去記過它在 llama 24K context 上會直接失敗。所以 filter 改成每批幾十篇、分批呼叫，和 L4 段落的分批是同一個模式；每批幾篇是 grade A 常數 `BATCH_SIZE`（`service_layer/filtering.py`）。改完之後任何模型的長提示分級都碰不到。
- **模型是 grade D 設定，換模型不改程式，但要先過評比。** `build_llm` 已支援 gemini、openai、anthropic 與 ai_gateway（`src/cyris/bootstrap.py:47-73`）。MVP 顯示 haiku 在四種新呼叫上不輸 gemini-3.8-flash 且便宜十倍，gpt-6-luna 便宜十六倍但段落太碎。生產的錢和品質主要花在 filter 的去留、summarize 的評分和 Clef，這三者沒比過，所以換模型排成 Lm 階段，收據是盲標 AUC，不是這份 MVP。時間壓力：gemini-3.8-flash 的導入價 2026-12-31 到期，2027 年起翻倍。

## 分階段計畫

每個階段一個可觀察的結果。只有一件事要等第二輪盲標抽完（約 2026-10-14，vault `pm/cyris/tasks/blind-labels-round-two.md`）：Lr 的正式站 D1 遷移，因為抽樣查詢以 `source_tier = 'filter'` 為鍵（`src/cyris/adapters/store/blind_labels.py:82`）；抽完之後標記頁與計分只讀 `blind_labels` 表存好的欄位，不再碰它。其餘階段的開發與試用部署都不等：試用租戶從空資料庫開機就是新 schema。原本「改版面的階段都等驗收輪」是為了 Clef 量投票行為，Clef 路線 2026-10-11 暫停（`clef-preference-order.md`）後這條理由不存在，2026-10-12 據此放寬。盲標第二輪改為 Lb 與 Lm 共用的測試集。

為了讓試用者早一點看到差異，2026-10-12 把實作順序定為 L1 → L3 → L4 → Lr → L2：L3 不等 L2，因為卡片預設就是單篇摘要，今天的 Features 卡直接當上層；L2 的掛接是例外路徑、每週約一張卡，對體驗貢獻最小，排最後。Lr 與 L1 不同時開，兩者都動 `SourceConfig` 與 `sources.config`，平行做整合必衝突。每個階段的票在 vault `pm/cyris/tasks/`，父卡 `m-digest-by-topic-and-area.md`。

## 什麼會推翻這個決定

- **對照卡片一張都沒有。** MVP 已經顯示嚴格同主題的掛接兩天只有一次，所以預設就是單篇。若上線後一個月裡確認過的掛接仍是零，掛接的確認步驟就刪掉，卡片回到純 Features，L2 只剩刪 `cluster_news`。
- **掛接錯得讀者看得到。** 標題餘弦有雜訊，錯掛的新聞出現在卡片底下的黃金位置。若讀者抽查的錯掛率高過事先定的數字，掛接門檻要收緊或改用內文嵌入。
- **領域退化成一個。** 今天 53 個來源有 30 個第一個標籤是 `tech`（見下方）。若 LLM 分出來的領域也是一個巨大的科技加幾個單來源的領域，骨架照類型就沒有地圖的作用，要改成以第二層標籤分。
- **提案爆炸或永遠不誕生。** 誕生門檻太低每期多出幾個領域；太高永遠只有冷啟動那幾個。N5 的值要在幾期內回頭看。
- **剩餘新聞的形式撐不起一期。** L0 已經顯示密度高文章每期一到兩篇，版面的主體是剩餘新聞。若 N1 選定的形式讓讀者覺得沒有卡片的期不值得打開，整個骨架要回頭檢討，而不是去補卡片。
- **權重跟不上興趣。** 若半衰期以週計仍趕不上選舉這種幾週的週期，或衰減回基線後讀者還是手動改基線，老化就沒有省到讀者的動作，L6 可以關掉。
- **分類錯放累積。** 讀者在 `/settings` 改來源領域的次數若持續上升，封閉集合的逐篇選擇就不夠穩，位置要退回只看來源層。

落選的方向，各附一句理由：
- tier 給基本分（例如 `filter` 40、`summarize` 60）再加逐篇的值：預設所有 tier 共用一條校準過的尺，ADR-0006 刻意不校準絕對門檻；40 和 60 沒有資料，`summarize` 從沒被盲標過；一個「每期最多升格幾篇新聞」的配額買到同樣效果，只有一個數字。
- 純品質排序當骨架：每期頁面長得不一樣，讀者養不出掃讀習慣；位置和價值完全共線，點開訊號分不出好還是在上面。
- 自由的 LLM 標籤當骨架：會漂移，期與期之間位置不穩；它留著合併主題用。
- 只看來源標籤當骨架：第一個標籤 30 個是 `tech`，會變成一個巨大區段；且來源跨領域時文章無法改選。
- 權重衰減到零：讀者對某領域的長期興趣不該因為一個月沒點開就消失。
- 權重改區段順序：每期頁面跟著近期點開晃動，回到純品質排序的問題。
- 沒點開當負訊號：看了標題覺得夠和不在乎是同一個觀測值（那邊「什麼會推翻」最後一條）。
- 扣著密度高的文章填之後的期數：對讀者不利。
- 只為 `summarize` 拉長窗口：被截掉的文章本來就留在 pending 等下一期，窗口不是瓶頸。
- 頁面上加「這篇放錯區」按鈕：讀者在 `/settings` 改來源的領域就是修正訊號，不加 UI。
- 修好新聞的 LLM 分群：嵌入分群在 0.70 就做出它做不出來的故事群，先消除再簡化。
- 只靠標題餘弦門檻掛接：0.55 到 0.60 之間有斷崖，0.60 掛上的一半不同主題（Marvell 配 AppLovin），門檻切不開，要 LLM 看內容確認。
- 掛接放寬到「同一領域的相關」、寫作時由 LLM 丟不相關：會出現硬湊的對照，而「忽略」欄位在 MVP 裡沒被檢驗到。
- 純合成段落當剩餘新聞的形式：99 篇只寫到約 15 篇，其餘消失，和「排序取代刪除」相反。
- 看了 MVP 的費用就直接換生產模型：MVP 只比了四種新呼叫，filter 去留、評分、Clef 三個花錢又定品質的步驟沒比，推理等級也不對等；換模型等 Lm 的 AUC。
- 為了 Haiku 的 100K 分級選別的模型：那是單一請求的門檻，不是用量門檻；最大請求離它十倍，而且 filter 分批（Lb）之後任何模型的分級都碰不到。
- 用 batch API 省每期 pipeline 的錢：三家都五折，但一期至少兩三輪串接的呼叫、每輪最長 24 小時，發刊時間不可預測，還要把 batch id 存進 D1 跨次喚醒，與 ADR-0010 相反；以 haiku 計一個月省 $0.21。batch 留給離線的整批工作：那邊 S5 的影子值、盲標批次評分、回填。
- 三層叫 `wire`、`column`、`follow`：The Wire 是現在的區段名，L3 換骨架後它會消失，名字留在設定裡變成歷史殘留。
- 三層叫 `news`、`essay`、`follow`：`news` 已經是來源標籤（`NEWS_TAG`），同一個字在 tier 和 tag 兩個欄位出現，讀設定的人會以為是同一件事。
- 密度高文章彼此先合併再掛新聞：L0 顯示每期只有一到兩篇，同主題的兩篇幾乎不會同期出現，多一個門檻換不到東西。
- 錨點跨期活幾天、收集後幾期的同主題文章：要多一列 §4、一個存活期，版面開始引用前幾期；讀者 2026-10-11 選了「同一期內用新聞補論點」，不跨期。

  - 費用與耗時，重跑一次帶計數（只含 MVP 的四種呼叫：領域提案、掛接確認、卡片、剩餘段落；不含 filter、評分、Clef、嵌入）。兩天合計：gemini-3.8-flash 24 次呼叫、輸入 39K、輸出 50K（含思考）、375 秒、$0.216；gpt-6-luna 25 次、43K、18K、196 秒、$0.013；claude-haiku-5-5 27 次、58K、44K、240 秒、$0.028。換成每天：$0.108、$0.007、$0.014；一個月約 $3.2、$0.20、$0.42，batch 五折再減半。官方價 2026-10-11：gemini-3.8-flash $0.75/$3.75 每百萬 token（2026-12-31 前導入價，之後 $1.50/$7.50，ai.google.dev/gemini-api/docs/pricing）；gpt-6-luna $0.10/$0.50（developers.openai.com/api/docs/models/gpt-6-luna）；claude-haiku-5-5 $0.10/$0.50（提示 100K 內）。三家 batch 都是五折。不對等之處：專案的 OpenAI client 固定 `reasoning_effort: low`，Gemini 與 Haiku 走預設思考，所以 gpt 的輸出 token 只有另外兩者的三分之一。Gemini 的輸出單價是另外兩者的 7.5 倍、又含思考 token，是它貴十倍的原因。
  - 領域由 LLM 從來源提出：兩天、兩輪，每次提出的名稱和分派都不同（同一天的 ByteByteGo 一輪在軟體工程、一輪在人工智慧與軟體工程）。印證領域要由讀者確認後固定，不能每輪重提。
  - 最大請求的大小，2026-10-11 用 10-07 的 233 篇新聞實際組出 filter prompt，token 依字數估（中文字 0.7、其餘每 4 字元 1 個，是估算不是計數）：摘錄 300 字元約 21K、500 字元（`cyris.toml.example:43` 的預設）約 22K、1000 字元約 26K、2000 字元約 31K，都是整天的量，一期約一半；30 天最忙的一天 301 篇依比例約 29K。MVP 的四種呼叫每次都在 10K 以下。會超過 100K 的只有多媒體：兩小時 podcast 逐字稿約 25K 到 30K 仍在內，YouTube 直接讀網址是 Gemini 專屬（`docs/milestones/multimedia-sources-podcast-youtube.md:58-63`）。長提示分級的官方來源同上一條。
